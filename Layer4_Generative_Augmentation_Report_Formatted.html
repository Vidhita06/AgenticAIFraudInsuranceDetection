ABSTRACT

Unmanned Aerial Vehicle (UAV) vision systems must operate under changing weather, lighting and viewpoint conditions, yet collecting real aerial imagery for every condition can be costly and limited. This project studies Layer 4 of a drone data augmentation pipeline: a generative augmentation engine that takes RGB views rendered from an existing 3D Gaussian Splatting (3DGS) reconstruction and edits their appearance with FLUX.1 Kontext. The current pilot uses the reconstructed 2_city scene, six camera views, and five target conditions—sunset, evening, night, heavy rain and snow.

The documented workflow renders six 1600 × 1200 RGB views and generates condition variants using FLUX.1 Kontext, with a fixed seed of 42 and JSON sidecar metadata recording prompts and generation settings. The supplied presentation reports 30 generated images, an output resolution of 1168 × 880, and approximately 38–40 seconds per image on a DGX GPU environment. Preliminary checks include condition-label matching, sharpness review, edge alignment, LPIPS, a pilot FID calculation and a baseline multi-view consistency measurement.

The results are interpreted conservatively. The FID value of 301.6 is labelled a pilot and not valid for a realism claim because only six images per condition were used and the reference set was the same scene’s six renders. Edge alignment is a two-dimensional proxy, not proof of 3D geometry preservation. The current status also identifies 23 images checked and seven excluded for now, with night outputs and one evening output provisional and being regenerated. Genuine object annotations and downstream real-UAV evaluation remain open. The report therefore presents a working controlled augmentation pilot, not a validated claim of geometry preservation or improved detection.

Keywords: UAV vision, data augmentation, 3D Gaussian Splatting, FLUX.1 Kontext, image editing, LPIPS, FID, quality control

1. INTRODUCTION

This chapter introduces the motivation for generative augmentation of UAV imagery, defines the problem addressed by Layer 4, and states the objectives and scope of the reported pilot. Layer 4 operates on 2D images rendered from an existing 3D scene; it does not reconstruct the scene or independently establish object ground truth.

1.1 Background

UAV imagery is used in surveillance, mapping, traffic monitoring, disaster response and environmental observation. A model trained on a narrow set of weather and lighting conditions may perform less reliably when the deployment environment changes. Collecting and labelling enough real images across every combination of conditions is expensive and operationally difficult.

A 3D Gaussian Splatting reconstruction represents a scene with Gaussian primitives and can render RGB images from specified camera viewpoints. These renders provide a repeatable visual starting point. FLUX.1 Kontext can then edit a supplied image according to a text instruction, for example introducing rain, snow or lower illumination while attempting to retain the original scene layout.

1.2 Problem Statement

The project addresses the limited diversity of environmental appearance in UAV training imagery. The technical challenge is to generate plausible condition-specific variants of rendered views while minimising unwanted changes to buildings, roads and scene layout. Since a generative model edits pixels rather than enforcing exact 3D constraints, each output must be evaluated and its limitations documented.

1.3 Objectives

  • Use the existing 2_city 3DGS reconstruction as the fixed scene source.
  • Render a controlled set of RGB views with documented camera parameters.
  • Apply FLUX.1 Kontext prompts to generate five environmental or lighting variants per view.
  • Record per-image generation parameters and metadata for traceability.
  • Review condition correctness, image quality and two-dimensional structural alignment.
  • Interpret LPIPS, FID and multi-view consistency without conflating their meanings.
  • Define a transparent review gate and identify which outputs remain provisional.
  • Prepare the pipeline for future evaluation against real UAV datasets and genuine annotations.

1.4 Scope

The report covers the Layer 4 pilot described in the supplied project presentation: 2_city rendering, six views, five conditions, FLUX.1 Kontext generation, JSON metadata and preliminary quality checks. The report does not claim that all outputs are accepted, that 3D geometry is preserved, or that augmented data improves a downstream detector.

Layer 2 is not treated as a mandatory dependency for running the Layer 4 image-generation pipeline. However, geometry/object-preservation evaluation requires genuine annotations correctly matched to the views. If those are unavailable, geometry evaluation remains not validated. The FID pilot is not treated as a valid realism benchmark.

1.5 Organization of the Report

Chapter 1 introduces the problem and scope. Chapter 2 reviews relevant methodological approaches and the research gap. Chapter 3 explains the proposed pipeline and evaluation methodology. Chapter 4 documents the system architecture and implementation settings. Chapter 5 presents the reported results and limitations. Chapter 6 concludes the report and outlines future work.

2. LITERATURE REVIEW AND RESEARCH GAP

2.1 Introduction

Layer 4 combines three established ideas: scene-based synthetic view generation, image-conditioned generative editing, and quality assessment of generated images. The project materials identify these as complementary parts of a pipeline rather than claiming that one method solves every issue. The review below is framed around the technical roles and limitations relevant to the implementation; exact bibliographic details should be checked against the team’s final reference list before submission.

2.2 Existing Approaches

Scene reconstruction and novel-view rendering provide a repeatable source of images from a common scene representation. 3D Gaussian Splatting is the source representation used in this project. It allows the team to render several camera views without acquiring a new real flight for each viewpoint.

Image-conditioned generative editing accepts both an input image and a text prompt. In this project, FLUX.1 Kontext is used to alter environmental appearance. This is distinct from a simple procedural overlay: the model synthesises image content according to learned patterns, which can improve visual plausibility but can also introduce unintended changes.

Image-quality evaluation is multi-dimensional. LPIPS measures perceptual feature difference between an original and an edited image; edge alignment compares visible outlines; FID compares distributions of deep image features across image sets; and multi-view metrics assess consistency between neighbouring views. These measures answer different questions and must not be treated as interchangeable.

2.3 Comparison of Representative Approaches

Table 2.1: Comparison of representative methods and project relevance

Approach Primary role Strength Limitation for this project
3D Gaussian Splatting Render scene views Fixed scene can produce repeatable viewpoints Rendering quality depends on reconstruction and camera setup; it does not provide object labels by itself
Procedural weather overlays Apply hand-coded visual effects Fast and deterministic May look artificial and does not learn scene-aware appearance changes
Image-conditioned generative editing (FLUX.1 Kontext) Edit a render using a prompt Can produce condition-specific appearance changes May alter structure, omit details or introduce artifacts; output must be reviewed
LPIPS Compare perceptual difference Useful for quantifying how much an edit changes appearance A high score may be expected for a strong condition change; it is not realism or task performance
FID Compare feature distributions of image sets Can compare generated and real image distributions when designed appropriately Unstable or misleading with very small, non-independent or inappropriate reference sets
Edge alignment Compare 2D contours Simple structural proxy Sensitive to darkness, haze, shifts and missing edges; not proof of 3D geometry preservation
2

2.4 Limitations of Existing Work

  • Generative editing can change scene details even when prompts request preservation.
  • Small pilot image sets do not support strong distribution-level realism claims.
  • Two-dimensional edge similarity is affected by lighting and image shifts.
  • Without matched ground-truth boxes or masks, object-preservation metrics such as IoU cannot be validly computed.
  • Visual plausibility does not guarantee that augmented images improve real-world detection or tracking.

2.5 Research Gap

The practical gap addressed by this pilot is an auditable pipeline that joins a fixed 3DGS scene, controlled camera renders, prompt-conditioned weather/lighting edits, per-image metadata and a transparent quality-review process. The contribution is an engineering workflow and a preliminary evaluation protocol. The current evidence is not sufficient to establish geometry preservation, broad realism, or downstream performance improvement; these remain validation tasks.

3. PROPOSED SYSTEM AND METHODOLOGY

3.1 Proposed System

The proposed Layer 4 system begins with the existing reconstructed 2_city scene. Six camera poses are used to render original RGB views. Each view is supplied to FLUX.1 Kontext with one of five target-condition prompts. The generated images are paired with JSON sidecars and passed to quality checks. Outputs are then classified for review or exclusion rather than automatically treated as validated training data.

3.3 Generation Method

FLUX.1 Kontext is used as an image-conditioned generative editor. The input is an original rendered RGB view and the condition prompt. Prompts target weather or lighting changes and include an instruction to keep buildings, roads and the overall layout unchanged. That instruction expresses the intended constraint; it does not mathematically guarantee that structure is preserved.

[Figure: Per-image generation and traceability]

The detailed presentation reports model ID black-forest-labs/FLUX.1-Kontext-dev, seed 42 for all images, guidance scale 2.5 for the baseline condition, 5.0 for heavy rain and 4.5 for snow. Reported output size is 1168 × 880, with approximately 38–40 seconds per image and around 34 GB GPU memory in the DGX environment. These are project-reported settings and should be confirmed against saved run logs before formal publication.

4.5 Implementation Workflow

  1. Load the existing 2_city 3DGS scene and confirm the renderer and camera configuration.
  2. Render six original RGB views and preserve the camera metadata.
  3. Create the five condition prompts with a shared scene-preservation instruction.
  4. Run FLUX.1 Kontext for each view-condition pair and save the generated image.
  5. Write a JSON sidecar for each output and validate required fields and image dimensions.
  6. Run condition, sharpness, edge-alignment and LPIPS checks; treat FID as a non-valid pilot only.
  7. Review provisional outputs manually, exclude uncertain images and document regeneration status.
  8. Export only reviewed outputs with traceable metadata for future downstream evaluation.

6. CONCLUSION AND FUTURE SCOPE

6.1 Conclusion

The Layer 4 pilot demonstrates a documented path from a reconstructed 3DGS scene to condition-edited RGB images using FLUX.1 Kontext. The supplied project presentation reports six original 2_city views and 30 generated variants across sunset, evening, night, heavy rain and snow. Generation settings and per-image JSON metadata provide a basis for traceability and repeatable experiments.

Preliminary checks include condition-label matching, visual sharpness review, edge alignment, LPIPS, a pilot FID calculation and a multi-view baseline. The results also reveal that evaluation must remain separated: LPIPS measures perceptual change, edge alignment is a 2D structural proxy, and FID depends strongly on a suitable reference set. The reported FID value is not valid evidence of realism, while object-level geometry preservation remains not validated without genuine matched annotations.

Accordingly, the current contribution should be described as a working controlled augmentation pipeline and preliminary quality-review workflow. It should not yet be described as proving geometry preservation or improving downstream UAV detection.

6.2 Future Scope

  • Regenerate provisional night and evening outputs, then re-run metadata and visual checks.
  • Increase the number and diversity of camera views and conditions.
  • Calibrate quality-gate thresholds using a documented validation set and human-review protocol.
  • Select a sufficiently large real UAV reference set and compare both unaugmented and augmented renders against the same reference for a defensible FID analysis.
  • Inspect candidate datasets for genuine annotations and camera/view correspondence before running bounding-box IoU or segmentation consistency.
  • Measure cross-view consistency on augmented variants, not only the original-render baseline.
  • Train/evaluate a downstream UAV detector on real benchmark data such as VisDrone or UAVid, with a controlled baseline and augmented-data comparison.
  • Capture exact model revisions, dependency versions, GPU details, logs and hashes for reproducibility.
  • Export accepted images with the correct annotations and metadata only after review; do not infer or fabricate labels.
